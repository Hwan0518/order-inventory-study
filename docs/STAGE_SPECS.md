# 단계별 고정 스펙 (Stage Specs)

이 문서는 각 단계의 **검증 기준과 확정된, 재현 가능한 스펙**을 관리한다.
`상태: 확정`인 섹션에 한해 엔티티/필드, 블랭크 처리할 메서드 시그니처,
Javadoc 문구(배경/구현 목표)까지 여기 적힌 그대로가 실제 보일러플레이트 생성의
유일한 소스다. 초안은 Q&A에서 검증할 후보이며 코드 생성의 근거로 사용하지 않는다.

**중요**: 이 스펙은 라이브 대화에서 즉흥적으로 만들어지지 않는다. 단계별 이론
Q&A는 "이 스펙을 확정하기 위한 저작(authoring) 과정"이며, 한 번 이 문서에
기록되면 이후 보일러플레이트는 항상 이 문서 그대로 생성한다 — 대화 내용이
달라져도 스펙이 바뀌지 않는 한 결과물은 동일하다. 이렇게 하는 이유는 이 학습
자료를 여러 사람에게 배포할 것이기 때문이다 (누가 받든 동일한 보일러플레이트).

이 커리큘럼은 이커머스 백엔드 실무에 곧바로 투입 가능한 수준을 목표로 한다.
질문을 고를 때 기준은 연차가 아니라 **트레이드오프 유무**다 — "정답이
하나뿐이고 이유를 설명할 필요조차 없는 전제조건"(예: "0이나 음수 수량을
허용해도 될까요?")은 구현 시 당연히 처리해야 할 사항이지 Q&A로 파고들 학습
목표가 아니다. "같은 요구사항을 만족하는 방법이 여러 개 있고, 그중 하나를
고르려면 트레이드오프(성능, 복잡도, 일관성, 장애 대응 등)를 근거로 판단해야
하는 설계 결정"(예: 재고 차감에 비관적 락을 거는 시점과 범위)만 학습 목표로
다룬다. 모든 단계의 Q&A/체크리스트/후속 질문을 저작하거나 검토할 때 이
기준으로 판별한다.

각 단계는 두 부분으로 구성된다.

- **검증 체크리스트(= 테스트 시나리오)**: Q&A를 시작하기 전에 먼저 고정
  작성한다. "무엇을 만족해야 하는가"(불변식/요구사항)만 담고 "어떻게
  만족시키는가"(락 종류, 패턴 이름 등 구현 기법)는 담지 않는다 — 그래서
  미리 공개해도 힌트가 아니라 문제 요구사항일 뿐이다. Q&A에서 나온 설계는
  이 체크리스트를 전부 통과해야 스펙으로 확정되며, 나중에 그대로 통합
  테스트 케이스가 된다.
- **확정 스펙**: 체크리스트를 통과한 설계를 엔티티/블랭크 메서드/Javadoc으로
  기록한 것. Q&A 완료 전까지는 "초안" 상태다.

### 확정 전 스펙 완전성 게이트

검증 체크리스트를 통과했더라도 아래 항목을 모두 결정해 기록하기 전에는
`상태: 확정`으로 바꾸거나 보일러플레이트를 생성하지 않는다.

- 각 엔티티의 패키지, 테이블명, 필드명, Java 타입, DB null/unique 제약과 ID
  생성 전략
- 연관관계를 객체 참조로 표현할지 식별자 값으로 표현할지
- JPA 기본 생성자, 제공 생성자/팩토리와 외부에 공개할 getter
- 리포지토리 포트별 정확한 메서드 시그니처와 반환 타입
- infrastructure에서 제공할 JPA adapter 및 Spring Data repository의 경계
- application 유스케이스의 입력/반환 타입, 트랜잭션 경계와 발생 가능한 예외 타입
- 사용자가 구현할 블랭크와 완성된 채로 제공할 보일러플레이트의 정확한 목록
- 블랭크별 Javadoc 최종 문구와 대응하는 검증 체크리스트 항목
- **자기 검토**: Q&A 스크립트의 모든 질문·상황 묘사·후속 질문이 위 트레이드오프
  판별 기준(정답이 하나뿐인 전제조건이 아니라, 여러 방법 중 트레이드오프로
  선택하는 설계 결정)을 통과하는지 하나씩 검토했는가
- **사실 검증**: 배경 문구와 상황 묘사가 실제 기술/실행 환경에 대해 거짓인
  진술을 하지 않는지(예: 동시 요청이 실제로 가능한데 없는 셈 치는 서술)
  검토했는가
- **실전 시험**: 저자 본인이 이 단계의 모든 질문에 트레이드오프를 고려한
  실제 답변으로 최소 한 번 직접 통과해봤는가. 이미 문서에 적혀 있던 내용
  (이전 세션·커밋에서 작성됐고 아직 이 항목으로 검토되지 않은 것 포함)이라는
  이유로 이 절차를 생략하지 않는다.

**중요**: 자기 검토·사실 검증은 `상태: 확정`으로 바꾸기 직전에만 하는 게
아니다. 초안 단계에서 질문을 문서에 적어 넣는 그 즉시, 학습자에게 실제로
보여주기 전에 먼저 스스로 적용한다. "아직 초안이니 나중에 검토하면 된다"고
미루다가 초안 상태 그대로 학습자에게 제시되는 사고(1단계 구 Q1, 구 Q3 사례)가
반복됐다. 질문을 한 줄이라도 쓰면 그 자리에서 바로 트레이드오프 기준에
대입해본다.

[`LEARNING_PROGRESS.md`](./LEARNING_PROGRESS.md) 체크리스트와 이 문서의 단계별
상태(체크리스트 공개 여부/확정 여부)는 항상 같이 갱신한다.

## 1단계

배경: 유통 채널 1개, 주문은 항상 결제까지 성공.

체크리스트 공개 시 제시할 상세 배경(고정, 문구 그대로 사용): `이 시스템은
하나의 온라인 판매 채널만 운영합니다. 고객이 주문하면 결제는 항상 성공하는
것으로 가정하고, 재고 확인·차감과 주문 기록까지 하나의 흐름 안에서
처리됩니다. 이 흐름은 여러 고객의 요청을 동시에 받을 수 있는 일반적인 웹
애플리케이션 위에서 동작하며, 같은 상품에 대한 주문이 동시에 여러 건
들어올 수 있습니다. 이 애플리케이션은 서버 인스턴스 1개로만 배포되어
있습니다(여러 인스턴스로 확장하는 시나리오는 이후 단계에서 다룹니다).`

### 검증 체크리스트 (= 테스트 시나리오) — 고정

- 재고가 충분할 때 주문이 성공하고, 재고가 정확히 차감된다.
- 재고보다 많은 수량을 주문하면 예외가 발생하고, 주문은 생성되지 않으며,
  재고는 변하지 않는다.
- 재고가 0인 상품을 주문하면 예외가 발생한다.
- 입고(재고 증가) 후 재고 수량에 정확히 반영된다.
- 존재하지 않는 상품을 주문하면 예외가 발생하고 주문 데이터는 생성되지 않는다.
- 한 상품에는 재고 레코드가 하나만 존재해야 한다.
- 성공한 주문의 주문 항목에는 요청한 상품과 수량이 정확히 기록된다.
- 여러 요청이 동시에 같은 상품을 주문해도, 성공한 주문들의 차감 합계와 최종
  재고 수량이 항상 일치한다 (초과 판매·Lost Update가 발생하지 않는다).
- (기본 입력 검증) 주문·재고 차감·재고 증가에 전달되는 수량이 0 이하이거나
  차감 후 재고가 0 미만이 되는 경우, 예외가 발생하고 재고·주문 데이터는
  변하지 않는다.

### AI 튜터 Q&A 스크립트 — 고정/비공개 판정용

AI 튜터는 질문 문구와 순서를 바꾸지 않고 한 번에 하나씩 제시한다. 질문과 함께
기록된 상황 묘사도 문구 그대로 질문과 나란히 공개한다. 각 질문 아래의 통과
기준과 후속 질문은 판정에만 사용하고 정답처럼 읽어주지 않는다.

상황 묘사는 배제할 기법·개념(예: "동시성 제어는 고려하지 않는다")을 직접
나열하지 않고, 구체적인 비즈니스 상황만 서술한다. 사용자가 그 상황으로부터
스스로 "그렇다면 무엇을 고려하지 않아도 되는지"를 추론하게 하는 것이 목적이며,
통과 기준 항목 자체를 서술하지 않는다. **상황 묘사는 실제 기술 환경(예:
애플리케이션이 멀티스레드로 동시 요청을 받는다는 사실)을 없는 셈 치도록
왜곡해서는 안 된다** — 비즈니스 단순화와 기술적 사실 왜곡은 다르다.

기본 입력 검증(0/음수 수량, 존재하지 않는 상품 등)은 이 단계 Q&A의 학습
목표가 아니다. 후속 질문도 이 주제로 유도하지 않는다.

**후속 질문 저작 원칙**: 후속 질문은 평평한 목록이 아니라 통과 기준 항목별
트리로 저작한다. 각 통과 기준 항목마다 최소 1차 질문을 매핑하고, 학습자가
그럴듯하게 틀리기 쉬운 항목(비자명한 함정이 있는 항목)에는 1차 질문의 답이
그 항목을 놓쳤을 때 같은 항목을 더 파고드는 2차 질문도 함께 준비한다. 튜터가
"이 항목엔 쓸 후속 질문이 없어서 다른 항목 질문으로 화제를 바꾸는" 상황을
만들지 않기 위함이다. AGENTS.md §5.2에 이 매핑을 사용하는 판정 규칙이 있다.

(구 Q1 "상품/재고/주문/주문항목에 어떤 확인과 변경이 필요한가"는 삭제됐다.
이미 체크리스트 공개 시점에 공개된 검증 체크리스트를 학습자가 자기 말로
재진술하게 시키는 것뿐이라 트레이드오프가 없었다. 아래 Q1~Q2는 그 자리에
있던 원래 Q2~Q3을 재번호한 것이다.)

#### Q1

질문: `여러 사용자가 동시에 같은 상품을 주문하면, 재고를 확인하고 차감하는 로직에는 어떤 문제가 생길 수 있나요?`

상황: `이 애플리케이션은 여러 요청을 동시에 처리할 수 있는 일반적인 웹
서버로 동작합니다. 같은 상품에 대한 주문 요청이 겹쳐서 들어올 수 있습니다.`

통과 기준:

① 서로 다른 요청이 같은 재고 값을 동시에 읽고 각자 계산한 뒤 저장하면,
  일부 차감이 반영되지 않는 Lost Update가 발생할 수 있다.

② 그 결과 실제로는 재고가 부족한데도 여러 주문이 함께 성공해 초과 판매가
  일어날 수 있다.

후속 질문 (통과 기준 항목별 매핑):

- ① 1차: 두 요청이 정확히 동시에 같은 재고 값을 읽어서 각각 차감을 계산해
  저장하면 최종 재고는 어떻게 될까요?
- ① 2차(1차 답이 "트랜잭션만 걸면 된다"는 식으로 넘어갔을 때): `@Transactional`을
  붙이는 것만으로 이 문제가 막힐까요?

#### Q2

질문: `이 문제를 막으려면 재고는 어느 시점부터 어느 시점까지 다른 요청의 접근을 막아야 하고, 그 범위는 왜 그렇게 잡아야 할까요?`

상황: `결제는 요청 하나 안에서 즉시 끝나므로, 상품 확인·재고 확인/차감·주문
기록까지는 하나의 트랜잭션 안에서 처리됩니다. 이 애플리케이션은 서버
인스턴스 1개로만 배포되어 있고, 트랜잭션이 붙은 메서드의 실제 커밋은 메서드가
반환된 뒤 프록시가 처리합니다.`

통과 기준:

① 재고 조회 시점부터 차감이 끝날 때(트랜잭션 종료·커밋)까지 다른 요청이
  같은 재고를 동시에 읽거나 변경하지 못하도록 막아야 한다.

② 이 범위를 필요 이상으로 넓히면(예: 잠금을 건 채로 무관한 작업을 수행하면)
  같은 상품에 대한 다른 요청이 그만큼 오래 대기하게 되어 처리량이 떨어진다.

③ 락을 거는 수단이 무엇이든(`synchronized`든 DB 락이든), 그 락이 실제로
  풀리는 시점이 트랜잭션이 실제로 커밋되는 시점보다 앞서면 안 된다. 단일
  인스턴스라 해도 메서드 안에서 `synchronized`로만 감싸면, `@Transactional`의
  실제 커밋은 프록시가 메서드 반환 후에 처리하므로 락 해제 시점과 커밋
  시점이 어긋나 아직 커밋되지 않은 값을 다른 요청이 읽어갈 여지가 남는다.
  DB 트랜잭션과 결합된 락(예: 비관적 락)을 쓰면 이 문제가 없다.

후속 질문 (통과 기준 항목별 매핑):

- ① 1차: 재고를 읽고 애플리케이션 코드에서 계산한 뒤, 트랜잭션이 끝나갈 때만
  값을 덮어쓰는 방식이라면 그 사이에 다른 요청이 끼어들 수 있을까요?
- ② 1차: 재고를 잠근 채로 이 요청과 무관한 느린 작업(예: 외부 API 호출)을
  수행하면 어떤 일이 생길까요?
- ③ 1차: 단일 인스턴스이니 `synchronized`로 재고 차감 메서드를 감싸면
  충분하지 않을까요? DB 락과 비교하면 어떤 차이가 있을까요?
- ③ 2차(1차 답이 "synchronized로 충분하다"고 단정하거나 타이밍 문제를 놓친

아래 엔티티/블랭크는 이전 논의(ARCHITECTURE.md 스타일 가이드 예시)를 바탕으로

### 엔티티 후보 계약 (domain)

모든 엔티티는 `dh.orderinventory.stage1.domain`에 둔다. 연관관계는 JPA 객체
참조가 아니라 식별자 값으로 표현한다. 모든 ID는 MySQL `IDENTITY` 전략의
`Long`이며, JPA용 `protected` 기본 생성자와 아래에 명시한 생성자/getter는
완성된 보일러플레이트로 제공한다. setter는 제공하지 않는다.

| 엔티티 | 테이블 | 필드와 제약 | 제공 생성자 |
|---|---|---|---|
| `Product` | `stage1_product` | `id Long` PK, `name String` not null, length 100 | `Product(String name)` |
| `Inventory` | `stage1_inventory` | `id Long` PK, `productId Long` not null + unique, `quantity int` not null | `Inventory(Long productId, int quantity)` |
| `Order` | `stage1_orders` | `id Long` PK, `createdAt Instant` not null | `Order(Instant createdAt)` |
| `OrderItem` | `stage1_order_item` | `id Long` PK, `orderId Long` not null, `productId Long` not null, `quantity int` not null | `OrderItem(Long orderId, Long productId, int quantity)` |

생성자 인자 자체의 형식 검증(`null`, 빈 상품명, 0 이하 수량)은 완성된
보일러플레이트에서 `IllegalArgumentException`으로 처리한다. 학습자가 구현할
도메인 블랭크는 `Inventory.decrease()`와 `Inventory.increase()`뿐이다.

### 리포지토리 포트 후보 계약 (domain)

아래 포트와 메서드는 블랭크 없이 제공한다. infrastructure에는 각 포트별 JPA
adapter와 Spring Data repository를 제공하며, Spring Data 타입은 domain에
노출하지 않는다.

```java
public interface ProductRepository {
    Optional<Product> findById(Long id);
    Product save(Product product);
}

public interface InventoryRepository {
    Optional<Inventory> findByProductId(Long productId);
    Inventory save(Inventory inventory);
}

public interface OrderRepository {
    Order save(Order order);
}

public interface OrderItemRepository {
    OrderItem save(OrderItem orderItem);
}
```

`InventoryRepository.findByProductId`의 JPA adapter 구현은 비관적 쓰기 락
(`@Lock(LockModeType.PESSIMISTIC_WRITE)`)으로 조회해, 재고 조회 시점부터
트랜잭션 종료까지 같은 재고 행에 대한 동시 접근을 차단한다. 이 락 힌트는
infrastructure에 보일러플레이트로 제공되며 포트 시그니처에는 노출하지 않는다.

### application 후보 계약

- `OrderService`는 `ProductRepository`, `InventoryRepository`,
  `OrderRepository`, `OrderItemRepository`를 생성자 주입받는다.
- 공개 유스케이스는 `Order placeOrder(Long productId, int quantity)` 하나다.
- `@Transactional`과 생성자 주입 코드는 제공하며 메서드 본문만 블랭크로 둔다.
- 0 이하 주문 수량은 `IllegalArgumentException`, 상품 또는 재고가 없으면
  `NoSuchElementException`, 재고가 부족하면 `IllegalStateException`을 발생시킨다.
  테스트는 예외 메시지에 의존하지 않는다.
- 입고는 1단계에서 별도 application 유스케이스를 만들지 않고
  `Inventory.increase()` 도메인 단위 테스트와 repository 통합 테스트로 검증한다.
